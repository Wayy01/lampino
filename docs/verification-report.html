1. Summary

The catalog was already fully database-driven. What was not driven by the database was everything around it: the hero text, every homepage section heading, the whole welcome block, the footer contact details, delivery pricing, the promo banner, and the special-offers page. Those were admin-editable fields that the storefront simply never read — an admin could type into them all day and nothing on the site would change.

All of that is now wired. Separately, twelve real defects were found in the admin CMS and fixed, the worst being that any validation error wiped every field the user had typed. No mock data remains in any read path.

Verified working end to end: product create / edit / delete (with images, variants, bilingual specs), rental package create / edit / delete, category create / edit / rename / reorder / delete, promotion create / edit / validation, admin user create with password hashing, order status change + delete with cascade, rental application submission from the storefront + status change, homepage & site settings forms, promo banner, special-offers page, cart with live delivery pricing, both locales (ro / ru).

6. Defects found and fixed

Critical

A validation error erased everything the user had typed. Reproduced live: on /admin/ro/products/new, fill in name, description and price, set a reduced price above the price, submit — the error rendered correctly, and every single field came back blank. React 19 automatically resets an uncontrolled <form action={fn}> the moment the action settles (startHostTransition calls requestFormReset before it even runs your action), and there is no opt-out on that code path. This hit all fourteen admin forms — products, rentals, promotions, the category and user dialogs, and every settings card.

Fixed with one shared AdminForm component that dispatches the action from onSubmit inside a transition instead of via the action prop, which skips the reset. Because useFormStatus only tracks the action prop, the pending flag is now published on a context that SubmitButton reads, so the spinners still work. Re-tested: the error shows and all four fields keep their values.

Data loss

  • Special-offers selection silently wiped. The form only renders the controls for the active selection method, so the other half posted nothing — but the action wrote all of it anyway. Switching from "manual" to "by category" and saving erased the entire manual product and rental selection with a cheerful "Saved." message. Now only the fields belonging to the submitted method are written. Verified by round-tripping manual → category → manual: all 7 products and 4 rentals survived.
  • Deactivating a product dropped it from the offers selection. The picker only listed active rows, so a previously-selected but now-inactive product rendered no checkbox and was quietly removed on the next save. Selected rows are now always listed, marked (inactiv).
  • A cleared delivery field saved as zero. Number("") is 0, which passed the "is it finite and non-negative" check, so the intended fallback was unreachable dead code — clearing "free delivery threshold" meant free delivery on every order. Empty input now falls back properly.

Crashes and correctness

  • Oversized price → unhandled 500. The columns are Decimal(10,2) and the inputs had no upper bound, so typing a long number produced a Postgres numeric field overflow that escaped the action as a 500 error page with all input lost. Now validated server-side (product and rental, top-level and per-variant) with a translated message, plus a max on the inputs. Verified: bypassing the client-side max returns "Prețul depășește valoarea maximă permisă." instead of a 500.
  • Promotions expired a day early and single-day promotions were impossible. new Date("2026-08-12") parses as UTC midnight while the status helper compares against local time, so in Moldova (UTC+2/+3) a promotion ended at 02:00 or 03:00 on its stated final day. And the validation rejected start === end outright. Dates are now parsed as local, the end date runs to 23:59:59.999 of its own day, and only a genuinely earlier end date is rejected. Verified: a 12 Aug → 12 Aug promotion saves and reads Active on 12 Aug.
  • Variant updates weren't scoped to their parent. The variant id came straight from a client-controlled hidden JSON field and was never checked against the product being saved. Two consequences: a second browser tab that had deleted a variant made the whole save throw P2025 and roll back, losing every edit; and an authenticated editor could rewrite a variant belonging to a different product. Now scoped with updateMany, so an unknown id matches nothing instead of exploding.
  • Variant reduced prices were never validated. A variant priced at 100 with a "reduced" price of 150 saved happily and rendered as a struck-through 150 against 100 on the storefront. Now checked, along with negative prices and non-integer stock.

Security

  • Upload could write an attacker-chosen extension into a public directory. The file kind was decided from the MIME prefix, but the extension fell back to the client-supplied filename — so Content-Type: image/x-anything with evil.html landed at public/uploads/images/<random>.html, served same-origin. The extension now comes only from a strict MIME allow-list.
  • SVG upload removed. image/svg+xml was explicitly allow-listed. An SVG served from /uploads/ can execute script in the site's own origin, and uploads are rendered unoptimized. Dropped from the allow-list.

7. Known gaps — not fixed, flagged for a decision

These are real, but each one is a product decision rather than a bug, so I've left them alone and am reporting them instead.

  • The role column is decorative. requireAdmin returns as soon as any valid session exists; nothing anywhere reads session.role. A user created as "Editor" can delete every product, every order, and can open /users and reset the owner's password. Either enforce the two roles or remove the role selector, because right now it implies a restriction that does not exist.
  • Sessions survive deletion. Auth is a stateless signed cookie with a 7-day lifetime and no per-request database lookup (deliberate — it's fast). But deleting a user does not revoke their session; a departing employee's open tab keeps full admin access for up to a week. The only lever is rotating ADMIN_SESSION_SECRET, which logs everyone out.
  • No rate limiting on the login form, and a timing difference between "no such user" (fast) and "wrong password" (~100ms of scrypt) leaks whether a username exists.
  • Promotions still don't affect displayed prices. An admin can attach a product to a promotion with a discount percentage and a date window, and the storefront will keep showing the plain reducedPrice. Wiring this up means deciding how a promotion percentage and a per-product reduced price interact when both are set — a pricing decision, not a code fix.
  • Orders can only be read, never created, in the admin. Product checkout hands off to WhatsApp and never writes an Order, so the Orders screen can only ever show seeded or manually-inserted rows. This matches the documented design; noting it because "12 orders" on the dashboard is seed data, not sales.
  • Singleton settings tables only expose row 1 (every action uses findFirst orderBy id asc). If a second row ever appears it is unreachable and undeletable through the UI.
  • SEO metadata is hardcoded in Romanian on every page regardless of locale, and there is no schema field for it.
